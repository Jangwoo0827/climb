# 클라이밍 도우미 · 기술 구현 정리 (면접용)

한 줄 요약: 벽 사진 한 장 → 홀드 위치 검출 → 홀드 종류 분류 → 코스 탐색 → 자세 계산 → 점수 순위 → 3D 표시.

## 1. 전체 흐름

| 단계 | 하는 일 | 방법 | 파일 |
|---|---|---|---|
| 1 | 홀드 위치 찾기 | Roboflow 공개 모델 holds-tptrk (신뢰도 0.4 이상). 모델 자체는 직접 학습하지 않음 | `rfDetect.js` |
| 1' | 루트 색으로 거르기 | Lab 색 공간에서 누른 홀드의 색을 구해 같은 색 상자만 선택 | `detect.js` |
| 2 | 홀드 종류 분류 | MobileNetV3-Small 직접 학습 → ONNX → 브라우저(onnxruntime-web) | `holdModel.js` |
| 3 | 코스 탐색 | 상태 (왼손, 오른손)에서 다익스트라 | `route.js` |
| 4 | 자세 계산 | 손은 홀드에 고정, 엉덩이 위치 격자 탐색 + 2관절 역운동학(IK) | `stickman.js`, `animate.js` |
| 5 | 후보 순위 | 보상 함수로 자세 점수를 매겨 1·2·3위 | `reward.js`, `rank.js` |
| 6 | 3D 표시 | 벽 앞 깊이(z) 추가, three.js, 홀드 종류별 손 모양 | `depth.js`, `hold3d.js`, `hand.js`, `View3D.jsx` |

기술 스택: JavaScript, React 19.2, Vite 8.3, three.js 0.170, onnxruntime-web 1.30, PyTorch 2.14(학습), Capacitor 8.5(안드로이드 앱).

## 2. 단계별 구현

### 2-1. 홀드 검출
- 사진을 긴 변 1280px로 줄여 Roboflow에 보내고, 홀드마다 상자와 신뢰도를 받는다.
- 개발 서버에서는 서버가 API 키를 들고 있고(중계), 배포판(GitHub Pages)에서는 사용자가 넣은 키를 그 기기에만 저장한다. 키가 앱 코드에 들어가지 않게 한 것.
- **앱에서 서버로 사진이 나가는 유일한 단계**다. 나머지는 전부 브라우저 안에서 처리한다.

### 2-2. 홀드 종류 분류
- 학습: ClimbingHoldType 약 1,895장 + 보조 데이터(hold classification Capstone), PyTorch로 MobileNetV3-Small fine-tuning.
- 클래스: 저그, 크림프, 핀치, 포켓, 슬로퍼. 볼륨(벽에 솟은 큰 면)은 모양 규칙(곧은 모서리의 다각형인가)으로 따로 판정한다.
- 실제 벽 사진 55장에서 76.4%. 모델 크기 6.1MB, 홀드당 약 36ms.
- 학습 때와 같은 방식으로 입력을 만든다: 홀드 상자(여유 5~10%)만 잘라 회색 바탕 224x224 가운데에 놓고 ImageNet 평균·표준편차로 정규화(주변 홀드가 섞이지 않게).
- 확률 분포(`probs`)를 그대로 남긴다. 애매한 홀드를 한 종류로 단정하지 않고 난이도 감점을 확률 가중 평균으로 쓴다.
- 홀드를 하나씩 처리하고 사이마다 화면에 차례를 넘겨서(`setTimeout 0`) 홀드가 많아도 앱이 멈추지 않는다.

### 2-3. 코스 탐색 (다익스트라)
- **상태** = (왼손이 잡은 홀드, 오른손이 잡은 홀드). 한 번에 한 손만 옮긴다.
- **끝** = 두 손이 모두 끝 홀드를 잡은 상태.
- **비용**(작을수록 좋은 동작):
  - 이동 거리를 몸의 편한 거리로 나눈 값의 제곱(멀리 뻗을수록 급격히 비쌈 → 중간 홀드나 매칭으로 나눠 가게 됨)
  - 두 손 사이가 벌어질수록, 높이 차가 35cm를 넘을수록 감점
  - 내려가는 동작은 레벨별로 감점, 위로 가면 약간 보상
  - 큰 홀드 선호, 크림프·슬로퍼 같은 어려운 종류는 입문일수록 감점
- **점프(다이노)**: 팔이 안 닿거나 손을 허리 위로 유지할 수 없을 때만 허용하고 기본 비용 30으로 매우 비싸다. 꼭 필요할 때만 쓰인다.
- 몸 모델: 키 × 윙스팬 비율로 팔 벌린 길이를 구하고 도달 거리 등을 계산한다. 레벨(입문·중급·상급)로 값이 달라진다.
- **후보 3개**: 첫 코스를 찾은 뒤, 쓴 홀드에 비용(+1.5)을 얹어 다시 탐색 → 서로 다른 코스를 얻는다.

### 2-4. 자세 계산
- 손은 홀드에 고정한다. 엉덩이 위치와 상체 기울기를 격자로 탐색해, 규칙을 가장 잘 지키는 자세를 고른다.
- 규칙(내 경험 기반): 손은 항상 엉덩이보다 위 / 발은 홀드나 벽에만 / 체중은 딛은 발 위 / 팔은 약 85%만 펴고 매달림.
- 팔꿈치·무릎은 **2관절 IK**(코사인 법칙)로 구한다. 후보가 두 개 나오는데, 팔꿈치는 어깨-손 선의 아래쪽으로만 꺾는다(닭 날개 자세 금지).
- 애니메이션은 매 프레임 IK를 다시 풀기 때문에 움직이는 동안에도 뼈 길이가 변하지 않는다. 몸은 스프링으로 움직인다.
- 손발은 한 번에 하나씩 옮긴다. 발을 먼저 올리고, 그래도 손이 안 닿으면 손을 먼저 옮긴다.

### 2-5. 점수와 순위 (보상 함수)
- 자세 하나하나를 **보상 함수**로 채점한다(몸 올리기, 손·발 홀드 확보, 3점 지지, 무게중심 안정, 다리로 버티기, 팔 펴고 매달리기, 관절 한계 장벽 등 11개 항목 + 움직임 크기).
- 무게중심 안정: 손발이 만드는 다각형(볼록 껍질)과 무게중심 사이 거리로 계산한다.
- 코스 점수 = 프레임 점수의 **평균**. 합계로 하면 프레임이 많은 긴 코스가 유리해지기 때문이다.
- **중요한 사실: 강화학습으로 학습한 것이 아니다.** 강화학습용으로 정리한 보상 명세를 가져와 2D 자세 채점기로 옮겨 쓴 것이다(가중치는 같은 값, `scripts/reward-check.mjs`로 일치 검사).

### 2-6. 3D 보기
- 정면 2D 자세에 깊이 z를 붙인다: 골반 약 0.12×키, 어깨 약 0.15×키, 손발은 벽(0).
- 팔꿈치·무릎은 실제 뼈 길이를 지키는 3D 2관절로 다시 계산한다.
- 홀드 종류별로 두께와 손가락이 닿는 지점, 손 방향이 다르다(`hold3d.js`). 손 모양(`hand.js`)은 종류별 손가락 굽힘 각도 표다(저그 [60,80,40]도 등).

## 3. 한계 (먼저 말하는 게 낫다)
- 분류 정확도 76.4%는 55장 기준이라 표본이 작다. 저그 학습 사진이 적은 게 병목이었다.
- 위치 검출은 공개 모델이라 틀리면(놓치거나 잘못 잡으면) 그대로 이어진다.
- 코스 탐색은 홀드 위치와 몸 모델 기반이지 실제 등반 데이터 학습이 아니다.
- 오버행(꺾인 벽)과 사용자 맞춤 체형은 이번 범위에서 제외했다. 실사용자 검증도 아직 없다.
- 난이도(V등급)는 어림값이지 정확한 등급이 아니다.

## 4. 예상 질문과 답

**Q. 왜 위치 검출을 직접 학습하지 않았나요?**
공개 모델이 이미 홀드 위치를 잘 찾았고, 제가 부족한 건 위치보다 홀드 종류 구분이라고 판단해서 종류 분류에 학습 시간을 썼습니다.

**Q. 위치 검출을 MobileNet으로 하면 안 되나요?**
분류 모델은 "이 사진은 무슨 종류인가"만 답해서, 여러 홀드의 위치까지 못 줍니다. 위치를 찾으려면 객체 검출 구조(상자를 예측하는)가 필요합니다.

**Q. 76%면 낮은데 쓸 수 있나요?**
틀려도 앱이 멈추진 않고, 확률 분포를 그대로 써서 애매하면 한 종류로 단정하지 않습니다. 사용자가 종류를 직접 고칠 수도 있습니다. 다음 단계는 실제 벽 사진에 직접 라벨을 붙여 다시 학습하는 것입니다.

**Q. 왜 다익스트라인가요?**
동작마다 비용을 줄 수 있고, 그 합이 가장 작은 경로를 보장하기 때문입니다. 상태가 (왼손, 오른손)이라 홀드 수 n이면 n²개뿐이라 브라우저에서도 빠릅니다.

**Q. 왜 강화학습으로 안 했나요?**
시간과 데이터 때문이고, 규칙으로도 사람이 이해할 수 있게 "왜 이 자세인지" 점수 항목별로 설명할 수 있기 때문입니다. 대신 보상 함수 설계를 가져와 채점에 썼습니다.

**Q. 제일 어려웠던 부분은?**
팔꿈치·무릎이 이상하게 꺾이는 문제입니다. 2관절 IK는 해가 두 개라 방향이 튀거나 몸통을 관통했는데, 꺾이는 방향을 고정하고 이전 자세와 가까운 해를 고르게 해서 해결했습니다.

**Q. 개인정보는요?**
사진은 위치 검출 단계에서만 Roboflow로 가고, 나머지 분류·탐색·자세 계산은 전부 브라우저 안에서 합니다.
